# What each client shows the model about skills

Checked November 22, 2026. The user-facing question is **“Can this client find my skill here, and what description does it have to choose from?”** A global folder scan, a client’s own registry, a version-matched rendering of the current settings, and a record of an earlier turn can each answer a different part of that question.

## Why the previous UI gave a blanket answer

The previous desktop UI interpreted a missing numeric budget as folder-only evidence. Its Sessions page told everyone outside Claude Code and Codex that their client did not record a listing. Those conditions reflected which readers Skill Studio had implemented. A missing number says nothing about what a client renders or saves. OpenCode provides a directly verified counterexample. [Listing dispatch and default](../../crates/skill-studio-core/src/listing_visibility.rs) · [Session dispatch and summary](../../crates/skill-studio-core/src/skill_sessions.rs) · [Skill detail](../../apps/desktop/src/components/SkillDetail/SkillVisibility.tsx)

## What the six built-in clients expose

### Claude Code

Claude documents both the overall listing budget and the per-entry cap on the combined description and `when_to_use`. The current worktree already predicts the listing and reads `skill_listing` attachments from session transcripts. Show the effective setting and its source, a preview for the selected scope, and a recorded listing when one is available. A missing model window belongs to the estimate. The installed CLI here reports 2.1.330. The existing Claude measurements were made against 2.1.327. [Anthropic’s skill budget documentation](https://code.claude.com/docs/en/skills) · [Existing measurements and versions](../agent-skill-conventions.md#model-listing-budgets)

### Codex

Codex has a native renderer for names, descriptions and file locators, with a token budget, truncation and omission. A rollout can contain the rendered skills block for that session. Keep the existing estimate and rollout reader. Compare copies using their resolved identities, because two files can have the same skill name. The installed CLI here reports 0.171.0. [Codex 0.171.0 renderer](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/ext/skills/src/render.rs) · [Recorded rollout comparisons](../agent-skill-conventions.md#model-listing-budgets)

### OpenCode

In 2.3.2 the registered inventory is available through `skill.list`. A separate instruction builder applies the selected agent and session permissions, excludes missing descriptions and disabled auto-invocation, sorts by ID and renders ID, name and description. The registered inventory alone can therefore overcount the model’s list. The checked 1.18.30 renderer also includes a location in its verbose listing. Select the implementation by version. [2.3.2 registry endpoint](https://github.com/anomalyco/opencode/blob/v2.3.2/packages/protocol/src/groups/skill.ts) · [2.3.2 listing builder](https://github.com/anomalyco/opencode/blob/v2.3.2/packages/core/src/skill/instructions.ts#L55-L77) · [1.18.30 system prompt](https://github.com/anomalyco/opencode/blob/v1.18.30/packages/opencode/src/session/system.ts#L103-L121) · [OpenCode’s source precedence and permissions](https://opencode.ai/docs/skills/)

OpenCode persists the `core/skill-guidance` state for a session. The initial baseline references structured values by hash. Later updates can include rendered additions, changes or removals. A read-only aggregate on this machine found a current-state blob with an ID, name and description in 213 of 305 session-state rows in one database and 295 of 351 in a second. The two database counts may overlap. Only table structure, JSON types and counts were read for this check. Describe the selected session state or update precisely. Its latest state alone cannot establish what appeared on every earlier turn. [Instruction persistence and baseline rendering](https://github.com/anomalyco/opencode/blob/v2.3.2/packages/core/src/session/instruction-state.ts) · [Upstream tests for listing changes](https://github.com/anomalyco/opencode/blob/v2.3.2/packages/core/test/skill/instructions.test.ts)

### pi

The 1.6.0 base prompt renders a skill’s name, XML-escaped description and file location. A manual-only skill stays available for explicit invocation. The skills section depends on whether a file-reading tool is available, and extensions can change the prompt for a turn. Use the installed version’s rules and identify the output as a base-prompt preview. [Skill loader and formatter](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/src/core/skills.ts#L349-L388) · [System prompt composition](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/src/core/system-prompt.ts#L171-L185) · [Extension hooks](https://github.com/earendil-works/pi/blob/v1.6.0/packages/coding-agent/docs/extensions.md#before_agent_start)

I ran the installed loader and prompt builder offline on two temporary skills, one normal and one manual-only. Both were discovered. With the read tool enabled, only the normal skill appeared, with the expected escaped ampersand and exact file location. With no tools selected, the skills section disappeared. This required no model request.

### Cursor Agent (CLI and IDE)

- **Discovery.** Cursor says the agent is “presented with available skills” and uses their descriptions to judge relevance. It scans project and user skill roots for Cursor, Agents, Claude and Codex, plus plugins and built-ins. Nested project roots and `paths` can scope skills to particular files. `disable-model-invocation: true` makes a skill manual-only. Conversely, the CLI keeps `user-invocable: false` skills available to the model while hiding them from slash autocomplete. [Cursor skills guide](https://cursor.com/docs/skills#how-skills-work) · [CLI release notes](https://cursor.com/docs/cli/changelog#jul-6-2026)
- **Inspect now.** The CLI’s `/skills` browser shows discovered skills and validation warnings. The IDE has **Customize → Skills**. In the installed CLI build, the Agent Client Protocol (ACP) sends `available_commands_update` after session creation or load. It combines commands and selectable skills into rows with a name and description, without a skill type or path. That can verify a picker entry. A model-only skill can be absent. The shipped CLI also builds structured skill metadata with a description, file path and invocation flags, and serializes a versioned discovery cache. Those records describe client-side discovery. They do not establish final server-side prompt text. [CLI skill browser](https://cursor.com/docs/cli/changelog#oct-8-2026) · [IDE skill browser](https://cursor.com/docs/skills#viewing-skills) · [Cursor ACP](https://cursor.com/docs/cli/acp) · [Versioned Cursor CLI distribution](https://downloads.cursor.com/lab/2026.11.13-eacade1/darwin/arm64/agent-cli-package.tar.gz)
- **Inspect a session.** The documented CLI JSON stream reports initialization, messages and tool calls. Skill Studio recognizes reads of a known skill file in Cursor transcripts. Neither source establishes the wording shown to the model. I found no supported per-turn listing export in the CLI references reviewed. Local version and help checks on 2026-11-22 identified CLI `2026.11.13-eacade1` and IDE `3.30.14`. The ACP finding comes from the shipped CLI code, without a live session. [CLI output format](https://cursor.com/docs/cli/reference/output-format) · [Skill Studio’s Cursor reader](../../crates/skill-studio-core/src/skill_uses/cursor.rs)

### xAI Grok Build (CLI)

- **Inspect now.** Run `grok inspect --json` in the project for discovered names, descriptions, source paths, user-invocation flags and disabled status. The TUI’s `/skills` tab also reads a catalog through the ACP extension `x.ai/skills/list`. Grok scans trusted project roots up to the repo root, user roots (including `.grok` and `.agents`), compatible Claude/Cursor roots, and bundled and plugin skills. Frontmatter `paths` can delay visibility until a matching file is touched. Under `[skills]`, `paths` adds locations, `ignore` hides paths and `disabled` keeps named entries visible in inspection but inactive. `disable-model-invocation: true` excludes a skill from the model listing. [Path-scoped skills](https://docs.x.ai/build/features/skills-plugins-marketplaces#skills) · [Discovery and settings](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/08-skills.md) · [Skills API](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/extensions/skills.rs) · [Model listing filter](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/types/skill_discovery_tracker/listing.rs)
- **Inspect a session.** xAI documents `chat_history.jsonl` as the saved model messages. Look for the rendered listing in the first user-message preamble or a later discovery reminder. The separate `system_prompt.txt` mirrors the system message alone. One template emits `<agent_skill fullPath="…">description</agent_skill>`; the text formatter starts “The following skills are available for use:” and includes an optional trigger and the skill path. The budgeted formatter allocates up to 400 bytes per entry for description and trigger combined, then can shorten descriptions, show names only, or omit entries. A compatibility template renders descriptions verbatim. The saved block establishes which form appeared in that session. [Session files](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/17-sessions.md) · [First-message renderer](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/prompt/user_message.rs) · [Formatting and limits](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/types/skill_discovery_tracker/listing.rs) · [Discovery reminders](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/types/skill_discovery_tracker/mod.rs)
- **Usage.** Skill Studio reads `updates.jsonl` for typed slash commands, skill tool calls and reads of a known skill file. A session can list a skill without any of those events. These Grok findings come from xAI’s public source dated 2026-09-29. No Grok executable was on the local PATH, so behavior of a current binary remains unverified. ## Catalog ownership and migration

The catalog thread confirmed that it owns one Rust registration per harness and the generated catalog **values** consumed by TypeScript. The visibility work owns the renderers, session readers and report consumed by the UI, CLI and MCP. Keep handwritten parsers for genuinely different client formats. Adding a client should require one registration and only the implementations for behaviors it supports. Preserve the existing client order and membership during the catalog move. [Current catalog and adapter](../../crates/skill-studio-core/src/harness.rs)

1. **Define the report at the catalog boundary.** Register discovery and copy precedence, current listing behavior, and historical listing evidence independently. Keep observed skill use, numeric limits and editable settings independent as well. Include the client version, scope, resolved copy or client ID, evidence source and, for a recording, session and sequence when available. A supported reader can still find no record on this machine. Keep that distinct from a missing reader and from a confirmed empty listing.
2. **Prove the design with OpenCode and pi.** OpenCode exercises both filtered current visibility and stored session state. pi exercises a reproducible listing without a numeric budget. Return these findings through the same core report that the existing Claude Code and Codex paths use. Replace the UI’s budget check and the default full-description state. Expose a setting only where the adapter knows its key, effective value, scope and owning source.
3. **Finish the remaining client adapters against their native evidence.** Verify the installed Cursor surface and the matching Grok Build revision. Show the actual description and any confirmed eligibility, cutoff or use rule. Lead with the strongest answer, such as “Available by slash command in Cursor” or “Listed in this Grok Build session.” When someone asks for session wording that the reader cannot verify, say “Skill Studio couldn’t verify the listing for this session.” Keep historical text separate from text read off disk today.
4. **Make the next client an acceptance case.** A synthetic seventh registration must appear in the core reports and desktop choices without an ID check in a view. For each shipped adapter, compare a small disposable collection against its native output: one normal skill, one hidden or manual-only skill if supported, and two copies with the same name. Assert the winning path or retained copies and the preview or recorded result. Include one settings or in-session change where that changes visibility. Keep Claude Code and Codex replay checks during migration. [Existing evaluation approach](skill-evals.md)

### Desktop integration

Client configuration and Skill detail use each report row’s `evidence` value. A `discovery` row shows the copies found in the client’s folders. A `preview` row can show the rendered description with or without a numeric budget. The latest saved listing can appear alongside either. **How [client] lists skills** opens the catalog’s release-specific behavior and links to its sources. This reference does not identify the version installed on the machine. In Sessions, open a session and then **Recorded listing** to inspect its saved entries. The report includes distinct description strings per client so that sessions sharing the same wording send it to the desktop only once. OpenCode, pi, Cursor and Grok Build still need their format-specific integrations described above.
