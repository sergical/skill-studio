# Flows

A new user-facing flow must add a row to this table and one flow-level test at
the lowest seam that proves its file effects. CLI and MCP parity comes from
the flow_parity.rs table, not from new tests per adapter.
The CLI and MCP columns name shared core calls. Gap rows are known missing
adapters or desktop integrations, not claims of feature parity. The flow_parity
integration test requires named CLI and MCP tests for each supported
flow. Those tests check result envelopes and file effects. It rejects missing coverage.
Coverage test names below are in apps/cli/tests/flow_parity.rs. Agent ids use open-code;
opencode remains an accepted input alias for compatibility.

## Timing

`pnpm run perf:baseline` times the read jobs and `tools/perf-writes.py` the write jobs. See
`docs/perf/README.md`.

Complete-tree regressions in `doctor_readonly.rs`, CLI, and MCP include lease files. ## Operation guarantees

The disk determines a skill's state. Scan reports the roots it could read and
keeps skills found in those roots when another root fails. Doctor checks the
whole scope, including links, ownership records, quarantine, and the journal.
Core filesystem operations stage writes and record inverse operations before
changing live paths. Copy removal moves bytes into quarantine so Undo can
restore them. Provider-owned installs and removals use the provider's CLI.

Harness detection and the editor picker share one cached login-shell probe
for PATH, VISUAL, and EDITOR. Detection runs in the blocking pool. A fallback
binary lookup reports its source; a folder alone does not prove that a CLI
is installed. See `docs/agent-skill-conventions.md` for agent roots and sources,
`docs/state-machines.md` for lifecycle transitions, and
`docs/perf/launch-detection.md` for launch measurements.

### Invariants

Doctor checks that each link resolves inside its root, each registry and
lockfile entry has a folder, no folder has two states, quarantine stays within
its retention cap, and the journal has no open plan at rest. Quarantine uses
`<root>/.skill-studio-quarantine/<id>`.

The app data folder's `schema_version` marker prevents an older app from
opening a folder written by a newer schema. A folder with no marker is version 0.

A pack is one source that ships skills: a skills.sh git source, an npm
package (`via`), a dotagents source or plugin, or a Claude Code or Codex
plugin. A skill from a folder on this machine (a dotagents `path:` source or
a skills.sh install from a local path) has no upstream, so it is not a pack.
Without `--remote` the call reads local files only. `--remote` runs
one `git ls-remote` and one shallow clone per git pack with the user's own git
credentials. Plugin packs show the agent's own update command; Skill Studio
does not run it.

`pack add`, `pack update` and `pack remove` plan first; `--dry-run` prints the
plan and changes nothing. `pack add` without `--skill` reads the source with
git to list its skills, also on a dry run. A real run gives each skill to
`add`, `update` or `remove`, so the tool that installed it writes the files,
and each skill gets its own event to undo with `restore`. Skills that share
a source and scope cost one `npx` call: `npx skills add <source> --skill a
--skill b` for add, and `npx skills update a b --global|--project` for each run of
consecutive skills.sh updates of one scope in `update_all` (#687). Requests
keep their order, and cancel is checked before each run. Each skill still
gets its own backup and event before the call, and a failed call fails each
skill it covered.
`crates/skill-studio-core/tests/write_spawn_count.rs` counts the calls. One exception:
`dotagents install` refreshes every declared skill in its scope, so the
dotagents skills of one scope share one event, and restoring it undoes all of
them. Update and remove skip plugin and npm packs, and skills with local
edits, which the owner tool would overwrite.

`pack add` always writes the shared `.agents/skills` copy that update and
remove use, and links each agent named with `--agent` to it. Without
`--agent`, the CLI and MCP write the shared copy only, which Claude Code does
not read. The desktop's pack add names the agents the Add Skill sheet ticks by
default: Claude Code, every detected agent and every agent kept in Settings
(`defaultSharedInstallAgents`). `pack update` refreshes each skill in place,
so it keeps the agents the skill already reaches.

Before the plan, each pack action and each single install, update or remove
that runs `npx` checks that `npx` is on `PATH`
(`crates/skill-studio-core/src/install_tools.rs`). If one is missing, the call
stops with one sentence that says to install Node.js. A git source that git
cannot read, or a missing git, also gives one sentence, not git's own output.
Pack add does not fall back to Copy: a Copy install is untracked, so the pack
would not show in Packs and could not update.

`pack export <dir> --skill <name>...` makes a new pack from installed skills
(design note on #615). It copies each skill's live copy in the scope (the
shared `.agents/skills` copy first, else an agent's own copy) into
`<dir>/skills/<name>/`, and writes `<dir>/README.md` with the
`npx skills add <source> --skill …` lines; `--source` defaults to
`<owner>/<repo>`. `<dir>` must be new or empty, and every file is created with
create-new, so nothing is overwritten. It is the one op that writes outside
the managed roots, and only into `<dir>`. It writes no lock, registry or agent
file and records no event: delete the folder to undo it. It refuses a parked
or plugin skill, an unknown or repeated name, and a link that leaves a skill
folder, before the first write. It opens each folder one step at a time from
`/` without following links and reads and writes only through the open
handles, so a folder swapped for a link during the export fails it instead
of redirecting it. It does not run git: push the folder yourself.
In the desktop, Pack on the selection bar asks for the new folder's name and
place (a save panel, so the folder does not exist yet), shows the plan, takes
the repository for the install lines, writes the folder, and shows the
install line with Copy. On Skills scoped to a project it takes each skill's
copy from that project; everywhere else, from the home.

`pack switch-source <source> <to>` moves the skills of a skills.sh pack to
another git source, usually the user's GitHub fork of it. Each skill runs
`npx skills add <to> --skill <name>` over its copy, so the skills CLI moves
the lock row itself, and each skill gets an `update` event that undoes the
folder and the lock row together. `--skill` moves only the named skills.
Skills with local edits are skipped; push those edits to the fork first.
Dotagents, plugin and npm packs are skipped: their source lives in a file
another tool owns. Before the first skill moves, `~/.agents/skill-studio.json`
records, for each skill by scope and name, the source it moves to and its
original (`pack_originals`), one record per source. A record counts only while the skill's lock row names its source, so a failed step or an undo finds the record that matches, with no rollback.
Moving a skill back to its original writes no reverse record. "Upstream" in a
pack report stays the pack's own source. `pack show
<to> --remote` then also reads the original and lists the installed skills
whose folder there differs from the fork's (`original.differs`), and the
skills only the original has (`original.not_in_source`). Skill Studio does not merge the two
or write to the fork: sync the fork on GitHub (`gh repo sync <to>`), then run
`pack update <to>`.

The desktop Packs page calls the same core operations. Each Update, Remove
and Add opens a dialog that runs the dry run first and lists every step with
its skip reason. Confirm runs the action, and the dialog then shows what each
step did. Plugin and npm packs show Update and Remove as off, with the owner
command in the tooltip.

Adding skills from a repo has one desktop flow, the Add Skill sheet, which
Packs → Add from a repo opens. Its picker shows a skill that already has a
live copy in the chosen scope as Installed: unchecked, not selectable, and
left out of the count and of Select all, since the core refuses to install
over an existing copy.

sessions in the last 30 days, the `usage` default window. The due list refreshes the same usage cache as
`skill-studio usage` and includes every usage observation when counts are
partial. A removed skill leaves the due list, and its date can still be cleared.
